- **Escopo:** implementação Rust do modo Plano (ativação, prompt, política `PLAN_MODE_ACTIVE`, `submit_plan`, aprovação interativa, projeções `PlanView`, eventos `PlanUpdated`/`ProfileChanged`, persistência em `code_events`) e do sistema de tarefas (`todo_write`, validação, projeção `todos`, evento `TodosUpdated`, contexto do prompt, uso em subagentes).
- **Método:** leitura integral dos arquivos-alvo + fluxo ponta a ponta (harness loop → tools → policy → broker → comandos IPC → projeção), confronto com `docs/goals/code-harness/{HARNESS,TOOLS,WORKBENCH,PLAN}.md` e com os testes existentes. **Nenhum `cargo build`/`cargo test` foi executado** (o verifier é dono disso); nenhum arquivo além deste foi alterado.

## Sumário executivo

1. **P0 — aprovar/negar um plano derruba a UI.** `submit_plan` grava `presentation = {"kind":"plan","state":…}`, mas o contrato do renderer (`ToolPresentation`) exige `{kind:'plan', plan: PlanView}`. Ao emitir `tool_call_finished` (e ao reabrir a sessão, porque o JSON é persistido), `ToolPresentationCard` passa `plan={undefined}` para `PlanCard`, que acessa `plan.markdown` → `TypeError` → `ErrorBoundary` da app inteira. O fluxo de revisão de plano é o único caminho que produz esse payload, então o defeito só aparece exatamente na feature auditada.
2. **P0 — plano aprovado não destrava execução no mesmo turno.** `ToolCtx.plan_mode` é um `bool` capturado uma única vez no início do turno (`harness/mod.rs:941`) e reutilizado em todas as chamadas do loop (`harness/mod.rs:1127`). `approve_plan` grava `plan/mode active=false` no banco (`session.rs:128-137`), mas o `ctx.plan_mode` continua `true`: qualquer `write_file`/`edit_file`/`run_command` no passo seguinte recebe `PLAN_MODE_ACTIVE`. "Aprovar e executar" só funciona se o usuário mandar uma **nova** mensagem (novo turno).
3. **P1 — `submit_plan` está dentro do wrapper de timeout de 60 s**, enquanto o timeout de aprovação é `approval_timeout_secs` (default **600 s**). Revisão humana normal (>60 s) termina em `TOOL_TIMEOUT`, o card fica fantasma na UI e o clique tardio é engolido (`resolve` retorna `false`, o comando devolve `Ok(false)`, o store ignora). A doc (`TOOLS.md` §4) promete 10 min por aprovação.
4. **P1 — as três saídas do plano não existem no contrato de aprovação.** `ApprovalOutcome`/`respond_approval` só carregam `decision/scope/feedback`; `CodeAgentWidgets` envia `approved` idêntico para "Aprovar e executar" e "Aprovar e revisar cada edição"; não há modo "revisar cada edição" na política (Editar auto-permite escrita) e o texto revisado do plano não é persistido (o backend grava o markdown do tool call).
5. **P1 — estado de modo desincronizado e não revalidado no turno.** `ProfileChanged` é emitido com `plan_mode: false` hardcoded quando o turno Code começa; `set_plan_mode` não emite `PlanUpdated` ao entrar/sair. A UI desliga o chip "Plano" durante todo o turno e, no sentido inverso, ligar o Plano no meio de um turno **não** bloqueia mutações (o `ctx` está congelado). O mesmo vale para `permission_mode` (ReadOnly ativado no meio do turno não bloqueia escrita).
6. **P1 — "Sempre permitir neste workspace" é uma regra morta** (duas causas independentes): `policy_check` monta `PolicyContext { workspace_id: None }` e `rule_from_request` grava `scope_id = NULL` para escopo workspace; `scope_id_applies` exige ambos `Some` e iguais. A funcionalidade documentada em `WORKBENCH.md` §8.4 nunca se aplica.
7. **P2 — tarefas:** `todo_write` declara `mutating: true` mas não passa por `policy_check`; `validate_todos(..., true)` e o parâmetro morto `allow_parallel_todos` fazem o agente principal aceitar vários `in_progress` (contra a própria guidance, o prompt e `TOOLS.md` §2.5); não é possível limpar a lista (`todos: []` → erro); subagentes não têm `todo_write` mas o prompt do filho manda usá-lo.

## Visão do fluxo atual (para referência)

```
chip /plan  → invoke set_plan_mode(true)            → code_events: plan/mode {active:true}
turno Code  → context::build (1x)                   → plan_mode=true, plan_view, todos
            → ToolCtx.plan_mode = true (congelado)  → prompt "Modo Plano ativo"
            → ProfileChanged{plan_mode:false}       → UI desliga o chip durante o turno
modelo      → submit_plan (ctx.plan_mode==true)
            → ApprovalRequested (options genéricas: allow/deny/allow_*)
usuário     → respond_approval(decision=approved)   → broker resolve
submit_plan → aprova; grava plan/submitted + plan/approved + plan/mode(false); emite PlanUpdated(approved)
            → presentation {kind:"plan",state:"approved"}  ← fora do contrato (crash da UI)
próximo passo → write_file  → policy_check(ctx.plan_mode==true) → DENY PLAN_MODE_ACTIVE
turno termina → novo turno relê o DB: plan_mode=false; agora funciona
```

## Questões em aberto / decisões do Lead

1. **Aprovação deve destravar o mesmo turno?** `WORKBENCH.md` §8.3 pressupõe que o agente edita logo após o approve. Se sim, o harness precisa revalidar `plan_mode` por passo (B-02) e informar o modelo. Se a decisão for "termina o turno e o usuário reenvia", então o texto de `submit_plan` ("continue a implementação") e a doc precisam mudar — e ainda assim o chip/estado precisa ser corrigido (B-05).
2. **O que é tecnicamente "Aprovar e revisar cada edição"?** Novo `PermissionMode::Review` (mexe em `domain.rs`, `types.ts`, política, UI, serialização de conversa) ou flag efêmera de sessão (`review_writes`) que force `Ask` para `RiskClass::Write` até o fim do turno? Precisa de contrato compartilhado (`respond_approval` + `ApprovalOutcome.options`).
3. **"Editar plano antes de aprovar"**: o texto revisado chega por qual campo? Recomendo `plan_markdown: Option<String>` em `respond_approval` (não reciclar `feedback`, que já é usado pelo "continuar planejando").
4. **Card do plano deve oferecer "Sempre permitir"?** Hoje `approval_options()` inclui escopos para `submit_plan`, gerando regra exata nos 600 primeiros chars do plano que **nunca é consultada** (B-04/B-17). Recomendo options específicas do plano (aprovar/revisar/continuar) e remover escopos.
5. **`todo_write` no modo Plano:** permitido (estado de sessão) ou negado (`HARNESS.md` §6.2 lê "tool mutante")? Se permitido, `mutating: false`/`risk: Read` e documentar; se negado, chamar `policy_check` (B-10).
6. **Lista vazia e limite:** permitir `todos: []` para limpar? Manter o teto de 50 (documentar) ou remover? (B-12)
7. **Subagentes e tarefas:** a doc (`TOOLS.md` §2.5) e o prompt do filho dizem que o subagente mantém lista; o catálogo reduzido exclui `todo_write`. Recomendo manter o subagente sem `todo_write` (é read-only) e corrigir doc/prompt; se a intenção for permitir, o filho precisa de `todo_write` no catálogo (com estado efêmero) e o parâmetro `allow_parallel_todos` precisa atravessar de verdade (B-11).
8. **`PlanState::Inactive`:** snapshot sempre `Some(PlanView)` com `Inactive` ou remover a variante do contrato? (B-15)
9. **Projeção única:** unificar em `harness/code/session.rs` e fazer `commands/code.rs` delegar (B-09) — cruza as áreas de harness-dev e code-runtime-dev; requer coordenação.
10. **Timeout de pausas humanas:** remover `submit_plan` do `default_timeout_ms` e alinhar `submit_plan`/`ask_user` ao mesmo padrão (`TOOLS.md` §4, 10 min) (B-03).
11. **Revalidação de modo no turno:** além de Plano, `permission_mode` e `trusted` também são congelados no `ToolCtx`/`WorkspaceHandle` no início do turno. Ativar ReadOnly no meio de um turno **não** bloqueia escrita hoje. Decidir se a regra vale por passo (recomendado) e se a UI deve bloquear a troca durante o turno.
12. **Semântica do `ProfileChanged`:** emitir por turno (snapshot) ou só quando muda? O reducer do `codeStore` aplica direto; com a correção de B-05 a semântica importa para não gerar eventos redundantes.
